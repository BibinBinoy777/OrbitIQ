# Phase 2: scientific validation and orbital analysis report

## Acceptance summary

**Phase 2 PASS within the explicitly retained TEME-only scope.** This establishes
stronger numerical verification, time/provenance contracts and accurate scientific
presentation. It does **not** establish complete scientific correctness,
observational orbit accuracy, quantified uncertainty or public-launch readiness.
No later phase was implemented. No commit, push, deployment or publication occurred.

## Initial findings and plan

Inspected Git status/structure, `docs/phase-1-report.md`, README, Phase 1 scientific
guide, product foundation, fixture provenance, all existing scientific tests,
SGP4/OMM initialization, API, storage/migrations, dependencies and React behavior.
The repository remains on unborn branch `work`, with project files uncommitted.
The original schema-2 database contained one actual ISS snapshot. Its byte-level
fingerprint and record count were recorded before code changes. The explicit
pre-code plan and risk ranking are retained in `phase-2-plan.md`.

Audited baseline: python-sgp4 **2.27**, WGS72 gravity, improved mode through the
OMM initializer; CelesTrak GP JSON/OMM input (TLE verification fixtures only),
UTC epoch normalization, two-part Julian-date SGP4 calls, geocentric TEME vectors
in km and km/s, ±7-day request window and model error handling. Astropy **7.2.3**
was installed but no frame transformation existed. The frontend was health-only.
The old 24 published-vector comparisons already covered moderate-eccentricity
near-Earth, deep-space/resonant and negative-offset cases.

Scientific gaps ranked before implementation:

1. High: immutable source linkage was not rechecked before propagation; corrupted
   provenance or numeric failures could escape a safe scientific API contract.
2. High: untyped scientific responses and a health-only UI could leave users
   unclear about units, frame, calculated-vs-observed status and limitations.
3. Medium: missing nearly-circular/low-perigee LEO references and explicit time,
   fractional-offset and input-boundary tests.
4. Medium: coarse implicit-clock freshness labels conflated no confidence model
   but did not adequately distinguish epoch age, retrieval age and unknown data.

## Corrections and retained behavior

- Retained the established SGP4 algorithm, WGS72 initialization, valid propagation
  behavior and every original reference assertion. Added guards for malformed or
  nonfinite vectors, numeric overflow and unrepresentable UTC times. No fallback
  positions, independent SGP4 implementation or loosened tolerance was added.
- Added typed response schemas: three-component finite vectors, explicit units,
  UTC/epoch/target/execution times, frame/model/library metadata and unquantified
  uncertainty. The actual source snapshot/hash remains the immutable input
  reference rather than duplicating orbital records per position response.
- Separated read-only application orchestration into `services/analysis.py`.
  Before calculation it checks exact raw hash, raw-record correspondence,
  normalized elements/units, catalog/epoch, UTC retrieval time, official source
  parameters and validator/library metadata. Corrupt provenance returns safe 503.
- Added deterministic pure freshness classification and optional bounded policy
  configuration. The response exposes epoch and retrieval ages separately.
- Preserved existing endpoints, health response, vector keys, timestamp strings,
  legacy flat freshness and error `detail`. Additive errors include stable codes.
  Numeric Unix timestamps and unsupported frame queries are intentionally rejected
  rather than accepted or silently ignored. Validation errors omit submitted
  values/context; unexpected response-schema failures return a safe structured 500.
- Added a read-only snapshot/propagation UI with loading/empty/error states,
  historical selection, scientific labels, provenance, units and limitations.
  It never triggers ingestion or performs orbital calculations in JavaScript.
- Browser review exposed JavaScript Date's loss of source microseconds. The UI
  now preserves up to six fractional digits when displaying UTC, and rejects
  impossible dates rather than normalizing them to plausible calendar values.
  Validation labels explain their limited scope in plain language.

## Frames, units and transformation decision

The only supported frame is **Earth-centered TEME**, true equator/mean equinox
of date in the SGP4/Vallado convention. State vectors have x/y/z in **km** and
vx/vy/vz in **km/s**; source angular units are degrees, epoch offsets minutes
inside SGP4 and days in API metadata. Scientific timestamps are UTC.

No TEME-to-terrestrial or other transform existed or was needed for correctness
of the existing API. None was added merely to expand scope. `frame=TEME` is
explicitly supported; ECEF, ECI, ITRS and GCRS return 422. There are **no supported
coordinate transformations to independently validate** in this phase; the
acceptance item is scoped to that fact, not a claim that a transformation passed.
No EOP dependency is introduced. Future terrestrial coordinates require Astropy,
explicit EOP/time policy and independent transform references before exposure.

The detailed axes, source conventions, nominal UTC-day behavior and limitations
are documented in `scientific-conventions.md`. TEME is never presented as an
interchangeable generic ECI/ECEF label. No longitude/latitude/altitude or globe
position is inferred from these Cartesian vectors.

## Freshness, uncertainty and provenance

Pure classification accepts explicit UTC `as_of`; the API evaluates once per
response. Defaults: fresh through **24h** epoch age inclusive; aging above 24h
through **72h** inclusive; stale above 72h. Optional exported thresholds must
satisfy `0 < ORBITIQ_FRESH_HOURS < ORBITIQ_STALE_HOURS <= 168`, all finite.

Missing/invalid/timezone-free epoch or retrieval time, or a future retrieval
relative to evaluation clock, produces **unknown**. Otherwise a future element
epoch is **future_epoch**. These rules are deterministic and boundary-tested.
Recent retrieval never refreshes an old epoch; historic snapshots are retained.
The legacy one-day flat labels remain for compatibility; new UI/client code uses
`freshness_info`, which explicitly states `accuracy_guarantee=false`.

Epoch, first retrieval, requested calculation time, actual calculation time and
freshness evaluation time remain distinct. Separate snapshot insertion time was
never recorded; `snapshot_created_at=null` explicitly communicates that absence.
No migration or invented historical timestamp was necessary.

Results identify catalog and immutable snapshot, hash/source, source epoch and
retrieval, target/execution time, SGP4 model and current library version, original
ingestion library/validator version, WGS72, frame, units, validation scope and
warnings. `kind=calculated`, uncertainty **not_quantified**, no covariance and no
observation-validation claim are explicit. No confidence percentages, direct
observations, collision probability, anomaly or orbital-safety claim exists.

## Remaining limits and recommended next phase

Validated scenarios are the six named published numerical cases, selected offsets,
wrapper input/time/metadata boundaries, and the stated UI/API/data checks. This is
not every SGP4 verification case, every orbital regime, every time scale or
observational validation. Negative-time independent vectors remain deep-space
cases; LEO timezone/negative fractional-time checks are consistency tests, not
new independent negative-time vector references. No covariance, uncertainty
estimation, residuals, anomaly/collision/safety analysis, terrestrial frame,
Earth-orientation policy, ground track or globe is implemented. Leap-second
strings and leap-second-crossing correctness remain outside the verified scope.
The seven-day bound/freshness bands do not establish an accuracy guarantee.

Recommended next phase, **only if authorized**: reference-tested TEME-to-terrestrial
coordinates and ground tracks using Astropy, with explicit EOP availability,
time/leap-second policy, error handling and reference tolerances before a globe
consumes those outputs. Production persistence, independent backups, security and
operations remain separate launch gates. No future phase has started.
