# Scientific conventions and validation scope

## Input, time and propagation

The ingestion format is CelesTrak GP JSON with OMM field names. TLE is used in
verification fixtures only; a public TLE ingestion/parser endpoint is not offered.
Required fields, finite values, source identity and CelesTrak's documented
Earth/TEME/UTC/SGP4 defaults are validated before ingestion. Explicit contradictory
metadata is rejected. Original bytes and normalized records remain separate.

SGP4 initialization uses **WGS72**, improved mode (`i`) through the established
python-sgp4 OMM initializer. The propagator remains python-sgp4; OrbitIQ does not
implement its own orbital algorithm. Input mean motion is rev/day, source angles
are degrees, eccentricity is dimensionless, BSTAR is inverse Earth radii, and
derivative fields retain CelesTrak/TLE conventions. Their units and conventions
are persisted; they are not measured accelerations or an uncertainty model.

CelesTrak's timezone-free orbital EPOCH means UTC by that format's definition.
API calculation times require a timezone and normalize to UTC. Unix-number query
timestamps and leap-second strings are rejected. Fractional seconds are supported
to Python datetime's microsecond resolution. Two-part `jday` input is passed to
SGP4, which interprets epoch offsets in minutes; the public offset metadata is
in days. Civil UTC days follow the SGP4 interface's nominal 86400-second day
convention; this is not a leap-second-precise TAI elapsed-time model. No claim
of leap-second-crossing propagation validation is made.

The supported request window remains ±7 days from the selected orbital epoch,
inclusive. An extra second beyond the boundary is rejected. This is a product
scope limit, not a predicted-accuracy or physical expiry guarantee. More than
24 hours from the epoch adds a limitation warning, independent of present-day
freshness. Historic snapshots are retained and can be calculated near their own
epoch; their age today is not silently substituted for the requested time.

SGP4 error codes, initialization failures, overflow, nonfinite/malformed vector
results and invalid calculation times fail explicitly. No zero vector or other
fabricated fallback is inserted. State vectors have exactly three components.

## Supported frame

| Property | Convention |
| --- | --- |
| Frame | **TEME**, True Equator Mean Equinox of date, as defined for SGP4 |
| Origin | Earth center |
| Axes | True equator and mean equinox of date; the SGP4/Vallado convention |
| Position | Geocentric Cartesian x/y/z, **km** |
| Velocity | SGP4 TEME Cartesian vx/vy/vz, **km/s** |
| Required metadata | Source element epoch/model, requested UTC time, WGS72 gravity constants |
| Position endpoint transformation | **None**; original vectors remain in the frame generated by SGP4 |
| Limitations | TEME is not a generic ICRS/GCRS `ECI` alias or an Earth-fixed/ECEF frame |

The original position query `frame=TEME` remains unchanged; other frames on that
endpoint return 422. Phase 3 adds **separate** Earth-fixed and ground-track
endpoints, retaining original TEME vectors in each result's `teme` object.

### Terrestrial path and time

Astropy **7.2.3** constructs `TEME(CartesianRepresentation.with_differentials,
obstime=Time(at, scale="utc"))` and transforms to geocentric `ITRS` at the **same
obstime**, following its official satellite documentation. Astropy's registered
Vallado 2006 path uses ERFA GMST82 with **UT1**, polar motion xp/yp, and no TIO
locator s' for this TEME convention. ITRS is explicitly named; generic ECI/ECEF,
GCRS and TEME are not aliases. No custom rotation or browser orbital math is used.
This is a conventional ITRS transformation, not an identification of a particular
ITRF station-network realization or proof of centimetre real-world accuracy.

Position units are km; the transformed differential is km/s in rotating ITRS,
not the original inertial velocity. Astropy's finite-difference transform uses
one-second total span (±0.5 s); EOP and leap validity are checked at these support
times too. Original TEME vectors, UTC target, source epoch/retrieval/hash and
SGP4 WGS72 provenance are retained. Astropy/pyerfa versions, method, EOP values,
source classification, file hashes and policy accompany the conversion.

UTC -> UT1 uses measured/predicted DUT1; UTC/TAI conversion uses local leap data.
TAI-UTC and UT1-UTC are distinct. Timestamp input resolution remains microseconds.
Leap-second strings are rejected by the existing API. Since the SGP4 wrapper's
nominal UTC-day propagation has not been validated across a leap transition, the
new terrestrial service also rejects requests where epoch-to-target TAI elapsed
time differs from nominal UTC elapsed time (`leap_crossing_unsupported`). This
preserves the existing position API without claiming new leap-crossing accuracy.

### Explicit Earth-orientation policy

No external download at application startup, request time, or in unit/reference
tests. Read the explicit local `astropy-iers-data` **0.2026.10.12.1.3.27**
`finals2000A.all` with `IERS_A.open`, never `IERS_Auto.open`, plus bundled
`Leap_Second.dat`. Parsed tables and hashes are cached in process. They are
replaced only by deliberate dependency updates and process restart.
Astropy configuration/table contexts are serialized with a process RLock;
`auto_download=False`, `iers_degraded_accuracy=error`, remote leap URLs empty,
and local system leap file selected. This avoids even remote-cache lookups on
first time conversion. The ERFA leap table is initialized from its built-in
history and updated from the explicitly selected local file. Other in-process
code using Astropy global configuration must respect this ownership; separate
workers have independent state.

At every sample, require valid, finite DUT1 **and** xp/yp, supported status codes
and coverage at all three support times. Missing files/parameters return 503;
negative range statuses return 422; no zero-DUT1, mean-polar-motion, extrapolation
or degraded-coordinate fallback is permitted. Non-policy Astropy/ERFA warnings
in the transform are promoted to explicit calculation failures.

| Setting / condition | Behavior |
| --- | --- |
| `ORBITIQ_EOP_POLICY=measured_or_predicted` (default) | Allow measured and IERS-A predictions; mark predicted results `predicted_eop` and warn they are not final measurements |
| `ORBITIQ_EOP_POLICY=measured_only` | Reject a sample needing prediction with `eop_prediction_disallowed` |
| IERS-A predictions with current UTC MJD minus table predictive MJD > 30 days | 503 `eop_predictions_expired`; no automatic refresh |
| Historical measured/final EOP | Supported within coverage regardless of current table age |
| Target/support date >= local leap-file expiry | 422 `leap_seconds_out_of_range` |
| Date outside EOP coverage | 422 `eop_out_of_range` |
| Invalid configuration / unavailable resource | Safe structured 503 |

The active table spans MJD **41684..61682**; predictive data start MJD **61315**.
The leap file expires **2027-06-28**. Actual usable coverage is the intersection
of EOP, leap validity, ±0.5 s differential support, policy and source ±7-day
window. EOP prediction age is a resource maintenance rule, not a satellite
uncertainty estimate. Predicted EOP are supported inputs with explicit status;
no claim that they are final measurements or fully observation-validated follows.

Updates: deliberately review a newer official `astropy-iers-data` package, run
`uv lock --upgrade-package astropy-iers-data`, install using `uv sync --locked`,
rerun reference/policy/regression checks and restart workers. Review the lockfile
change and new coverage/expiry before release. These are operator instructions,
not operations performed during Phase 3. Monitor approaching prediction expiry,
coverage and leap-file expiry before public hosting. Network absence does not
change results when valid local resources exist; otherwise calculations fail.

### Geodetic and sampling contract

ITRS Cartesian -> `EarthLocation.to_geodetic(ellipsoid="WGS84")`, followed by a
residual-checked exterior latitude correction as documented in
[Phase 6.1.1](phase-6.1.1-report.md). Latitude is
**geodetic**, degrees north in [-90,90]. Longitude is degrees east normalized to
**[-180,180)** (+180 maps to -180). Altitude is ellipsoidal height in **km** above
WGS84 (a=6378.137 km, f=1/298.257223563), not geocentric radius, mean sea level,
terrain clearance or observer elevation. WGS84 geodesy does not change the
unchanged **WGS72 gravity model** used by SGP4. Pole longitude is conventional
rather than a meaningful unique direction. Invalid/nonfinite coordinates and
positions within 1 km of the geocentre fail explicitly.

Read-only ground tracks require catalog ID plus an **explicit immutable snapshot**.
No implicit latest-source switching, ingestion, derived persistence or migration.
Validate interval ordering (equal endpoints produce one sample), source ±7-day
window and limits before propagation. Defaults: 60-second step, 361 samples,
24-hour maximum duration. Step must be an integer 10..3600 seconds.
`ORBITIQ_TRACK_MAX_SAMPLES` may be 1..1000 and
`ORBITIQ_TRACK_MAX_DURATION_SECONDS` 10..86400; invalid settings return 503.
Number of points = floor((end-start)/step)+1. Include start plus aligned samples
through end; **do not append an unaligned endpoint**. Requested and actual sample
bounds are UTC and explicitly distinct. Coordinates/sample times are deterministic
for fixed input/table; execution timestamps and present-day freshness are clocks.

**Atomic response contract:** one propagation, provenance or transformation
failure rejects the entire track with a structured error; there are no partial
responses and no fake/zero replacement points. No previously computed points are
returned as valid. Segment IDs increase when adjacent longitudes differ by >180°.
The UI starts a new polyline at these breaks and also leaves steps over five
minutes unconnected. It draws no interpolated antimeridian edge points. Lines
between sampled positions are presentation only, not a continuous ephemeris,
visibility assessment or collision/safety finding.

New routes:

- `GET /api/snapshots/{snapshot_id}/earth-fixed?at=<aware ISO>&frame=ITRS`
- `GET /api/satellites/{catalog_id}/ground-track?snapshot_id=<id>&start=<aware ISO>&end=<aware ISO>&step_seconds=60&frame=ITRS`

Both have finite typed response models, source validation and structured errors.
Unsupported frames/times/numeric bounds return 422. Snapshot absence and catalog/
snapshot mismatch return 404. A history-list query for an unknown catalog retains
its previous empty-list behavior. The old TEME endpoint is backward-compatible.

## Freshness and timestamps

`freshness_info` is the new authoritative age-presentation object. It is evaluated
using one explicit UTC `as_of` time per response, separately from requested
calculation time. Pure classification tests provide deterministic `as_of` values.
Default thresholds are 24 and 72 hours; optional exported configuration is
`ORBITIQ_FRESH_HOURS` and `ORBITIQ_STALE_HOURS`. They must be finite and satisfy
`0 < fresh < stale <= 168` hours. Invalid configuration returns a safe 503.
These are configurable product labels, not physical accuracy tolerances.

| State | Exact rule |
| --- | --- |
| unknown | Epoch/retrieval missing, invalid, timezone-free, or retrieval later than evaluation clock |
| future_epoch | Otherwise, element epoch is later than evaluation time |
| fresh | Epoch age from 0 through fresh_hours inclusive |
| aging | Epoch age greater than fresh_hours through stale_hours inclusive |
| stale | Epoch age greater than stale_hours |

The payload includes epoch age and retrieval age in **seconds**, evaluation time,
thresholds, `basis=orbital_epoch` and `accuracy_guarantee=false`. A recent download
of old elements remains stale. Future epoch or clock inconsistencies are explicit
rather than presented as fresh. No data is deleted due to age.

The legacy flat `freshness`, `epoch_age_days` and one-day `freshness_policy` fields
remain for compatibility; `recent/stale/future_epoch` do not provide the new
three-band policy. New clients use `freshness_info`, as the Phase 2 frontend does.
Missing epoch metadata can be shown as unknown in history, but a snapshot that
fails required scientific provenance checks cannot produce a calculated result.

Distinct timestamps:

- `orbital_epoch`: the source mean-element reference epoch.
- `retrieved_at`: first real source retrieval for that exact dataset; duplicate
  replay preserves it and is not a full audit log of later identical requests.
- `snapshot_created_at`: **null**, because a separate insertion timestamp was not
  recorded. It is never invented from retrieval time.
- `at`: the requested propagation time, normalized to UTC.
- `calculated_at`: actual calculation execution time.
- `freshness_info.evaluated_at`: the age assessment time.

The UI labels these separately, converts offsets to UTC, preserves up to six
fractional digits and refuses invalid dates instead of normalizing them into
plausible calendar values. Millisecond-only JavaScript Date formatting is not
used to discard available source microseconds. Vector rounding in the UI is
explicitly display precision, not a measure of orbit accuracy.

## Provenance, compatibility and safe errors

A propagation response retains snapshot/catalog identity, exact source URL,
response SHA-256, element epoch, retrieval time, requested/execution times,
input validation and validator version, ingestion SGP4 version, calculation SGP4
version, frame, units and explicit uncertainty status. The immutable snapshot is
the input reference; the complete orbital record is not duplicated in every
position response.

Before calculation the application service rechecks exact raw-response hash,
original-record correspondence, normalized elements, units, catalog/epoch,
retrieval timestamp, official source/query and validator metadata. Invalid stored
provenance returns safe 503. These hashes/triggers detect accidental corruption;
an administrator can rewrite a database and its hashes, so this is not a signed
or tamper-proof observational record.

Existing endpoints, vector keys, timestamp strings, snapshot references, health
behavior and legacy error `detail` remain. Position/list schemas and metadata are
additive. Numeric Unix timestamp strings, silently ignored frame parameters and
malformed stored provenance are intentionally tightened for scientific safety.
Errors add `{error: {code, message}}` while preserving `detail`; validation issues
exclude submitted input/context. Known failures use 404 (no snapshot), 422
(request/model-window/propagation), 503 (storage/provenance/policy), and a safe
500 if a generated scientific response fails its schema. Stack traces, internal
paths and sensitive submitted values are not returned.

## Numerical verification and uncertainty

The fixed Vallado AIAA 2006-6753 reference subsets and their provenance are
recorded under `backend/tests/fixtures/`. The original 24 comparisons are
preserved. Phase 2 adds 16 low-perigee/nearly-circular LEO comparisons at the same
absolute tolerances: **1e-5 km** position, **1e-8 km/s** velocity, relative tolerance
zero. These accommodate published precision and microsecond epoch representation.
`docs/phase-2-reference-results.json` records all inputs, epochs, target times,
expected/actual vectors and errors from the executed audit.

This numerical agreement is independent published-vector verification, not a
comparison of two OrbitIQ calls. Timezone/fractional/window tests are explicitly
self-consistency/boundary checks. Astropy time-input checks are independent of
SGP4's Julian-day conversion but do not verify an orbit or frame transform.

The API returns `kind=calculated` and `uncertainty.status=not_quantified`, with
no covariance, observation-validation claim or confidence percentage. No direct
observations, residuals, anomaly declaration, collision probability or orbital
safety conclusion are supported. Reference tests validate the selected scenarios
and implementation conventions; they do not establish complete scientific
correctness or a probability distribution for a real satellite's location.


## Phase 3 independent verification scope

See `backend/tests/fixtures/earth-fixed.json`, its fixture README and
`docs/phase-3-reference-results.json` for exact independent inputs, expected/actual
results, EOP assumptions and tolerances. Vallado Appendix C is tested with both
published fixed EOP (reference-only fixture) and active final IERS values. The
Astropy official satellite example supplies another epoch and full geodetic
expected result. SOFA/ERFA published geodesy and UTC->TAI/UT1 constants are
independent of OrbitIQ's wrapper, but the application intentionally uses the
Astropy/ERFA library stack; this is not a second independent physical model.
Analytic WGS84 axes/poles, wrapping, invalid values, EOP availability/status/age,
concurrency, source/time consistency and sampling limits are additional checks.
The original 40 SGP4 references and their tolerances remain unchanged.

Selected transformation agreement is numerical verification, not universal
terrestrial accuracy, observation validation or quantified prediction uncertainty.
The residuals and limited precision claims are explicit in the Phase 3 report.


## Phase 4 rendering and timeline conventions

Earth-fixed responses add `ground_position_km`: ITRS Cartesian **km** of the
WGS84 normal footpoint at zero ellipsoidal height, computed on the backend with
Astropy `EarthLocation.from_geodetic` using the validated geodetic latitude and
longitude. This is not a radial projection, observer location or another orbit.
The new field is additive; original TEME/ITRS vectors, source/EOP/time metadata,
limits and failure semantics remain unchanged. Analytic WGS84 axes and a
SOFA gd2gc reference with analytic normal-height removal test this output.

Three.js consumes actual ITRS satellite and footpoint vectors. Presentation maps
ITRS `(x,y,z)` to Three `(x,z,-y)`, dividing all components by 6378.137 km. This is
a right-handed display basis and uniform scale, not a new celestial/terrestrial
conversion. Earth is a tessellated WGS84 ellipsoid (polar/equatorial ratio
1-1/298.257223563); satellite centres retain the returned distance scale. No TEME
vector is placed directly on Earth. Missing/malformed required rendering vectors
or positions beyond the declared display extent (400 equatorial Earth radii)
disable markers rather than creating substitutes; metadata/2D remain available.

The surface overlay is lifted by a display factor **1.002**, roughly 12.8 km at
the equator, to avoid surface occlusion; it is clearly labelled illustrative.
Satellite glyph radius is exaggerated (0.02 display Earth radii), not a physical
size estimate. Static Earth imagery, tessellation and fixed fill lighting are
visual context, not precision cartography, terrain, sunlight or illumination at
the selected epoch. The texture is not a scientifically validated georeference.
Exact values belong to the numeric data panel. 3D paths connect only same-segment
samples <=60 s apart; coarser samples remain dots, avoiding long chords through
Earth. 2D retains its existing antimeridian and >5-minute gap rules. Both views
share the same backend dataset and selected sample; neither invents edge points.

Timeline playback advances one returned sample each real second with no
interpolation, orbital calculation or network request. A 60-second sampling step
therefore advances simulation time by 60 seconds per playback tick; it is not a
live observation stream. Requested propagation time, source epoch, first retrieval
and actual calculation time are distinct UTC fields. Reset selects the first
returned sample; playback stops at end, on interval/source change, fatal track
failure, hidden document or unmount. Reduced motion disables automatic playback
and retains keyboard/manual sample navigation. In-memory results are labelled
calculated from a stored snapshot; no derived history/timeline state is persisted.

Stored discovery uses an explicit NORAD-ID snapshot request. Source element
inclination (degrees), eccentricity (dimensionless), mean motion (rev/day) and
international identifier come from the existing validated snapshot-detail API.
No unsupported orbital parameter is invented to fill the panel. Previous
uncertainty, leap-crossing, EOP-maintenance and reference-residual limits remain.

## Phase 6.1 evidence and resource quality

The separate [Phase 6.1 assessment](phase-6.1-report.md) and
[structured evidence](phase-6.1-scientific-evidence.json) distinguish numerical
agreement, independent mathematical implementation checks, actual observations
and uncertainty quantification. That historical assessment recorded an unmet
high-altitude geodetic latitude precision target. The separate
[Phase 6.1.1 remediation](phase-6.1.1-report.md) now meets the original target
without a tolerance change, retaining the historical reports. Neither is an
accuracy certification. No independent satellite measurements were compared. Existing
`uncertainty.status=not_quantified` and `observation_validated=false` remain.

`earth_orientation.source_quality` is additive metadata for each central UT1 and
polar-motion sample, plus each velocity-support sample at -0.5, 0, +0.5 seconds:
`final` (IERS-B), `rapid_nonprediction` (IERS-A nonprediction), or `prediction`.
Legacy wire strings `IERS_A_measured` and aggregate `status=measured` mean
nonpredicted resource values; they do not certify IERS-A rapid estimates as final
or imply any satellite observation. Aggregate prediction policy still considers
**every** support sample, including a predicted side with a final central sample.
All coverage, expiry, maximum prediction-table age, and no-download rules remain.

The fixed-EOP Appendix C position residual is reproduced as 1.31736574 cm maximum
Cartesian component (1.32868009 cm vector norm). A controlled single rounded UTC
JD plus DUT1 evaluation of the published polynomial matches the paper to about
0.049 mm; the independent 50-digit evaluation agrees with the existing two-part
Astropy/ERFA result. This supports a dominant reference precision/order mismatch,
not a demonstrated runtime position defect. It does not certify the authors'
exact historical execution, remove remaining velocity/convention uncertainty, or
justify replacing the more precise two-part calculation. Original tolerances stay.

UTC, element epoch, first retrieval, insertion (where recorded), requested
calculation, execution, resource validity and any future observation time remain
distinct. SGP4 uses nominal UTC 86400-second days; TAI elapsed time across a leap
can differ. The terrestrial path continues to reject that unsupported interval
in either direction and the API rejects second-60 strings. Neither silently
changes to TT/TAI propagation nor extrapolates missing EOP.
